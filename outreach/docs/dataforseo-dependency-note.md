# DataForSEO Dependency & Migration Note v0.1

**Module:** `outreach-pipeline` (AR Tools)
**Siblings:** `PRD-prospect-pipeline.md`, `scoring-spec.md`, `storage-retention-spec.md`
**Purpose:** Written while calm. DataForSEO is a deliberate single dependency (PRD §15a); this
records what would break, what would replace it, and what to preserve now so a forced migration
is survivable.

---

## 1. What we depend on it for

| Use | Endpoint class | Substitutability |
|---|---|---|
| Maps geogrid — full pack at arbitrary lat/lng | Google Maps SERP | **Hard** |
| Organic SERP + paid-results parse | Google Organic SERP (advanced) | Easy — commodity |
| AI Overview capture | Organic SERP w/ AIO parameter | Moderate |
| AI Mode geogrid | Google AI Mode SERP | Moderate — few providers |
| LLM citation checks | LLM Responses / LLM Scraper | Easy — can go direct to model APIs |

Only the first is genuinely hard, and it is the one the whole economic model rests on.

## 2. The capability requirement most alternatives fail

The geogrid needs **the full local pack (~20 results) returned at an arbitrary coordinate, with
Google `place_id` on every result.** That is a narrower requirement than "Google Maps data," and
two common substitutes fail it:

- **Google Places API is not a substitute.** It returns Places' own ranking, not the local pack
  as a searcher sees it. Coverage measured against it would not mean what the audit claims.
- **Providers returning scraped names without `place_id`** force fuzzy matching across the entire
  prospect history. This is the migration killer — see §4.

Plausible candidates to evaluate if needed: SerpApi, Serpent API, Bright Data, Oxylabs, Apify.
Each must be tested against the two criteria above before anything else is considered.

## 3. Migration must be parallel-run, never cutover

**This is the most important line in this document.**

Delta claims are the strongest asset the system produces, and they compare a current snapshot
against the mean of the prior two. Providers differ in proxy pools, location simulation, and
result parsing. A hard cutover would therefore manufacture a **portfolio-wide false delta on day
one** — every prospect appearing to gain or lose coverage simultaneously, with the pipeline
happily generating "you dropped out of the pack last cycle" claims for all of them.

Required sequence:

1. **Parallel run.** Both providers scan the same grids on the same cadence for ≥3 cycles.
2. **Quantify the offset.** Per-submarket mean coverage difference and variance between providers.
3. **Decide.** If the offset is small and stable, splice with a documented adjustment. If large or
   unstable, treat the switch as a **series break**: mark it in `scan_snapshot`, suppress deltas
   spanning it, and restart delta eligibility at 3 post-cutover snapshots.
4. **Never** compute a delta across a provider boundary without an explicit, tested adjustment.

Budget ~6 weeks and roughly double scan cost during parallel run. At current spend that is
trivial money and the only safe path.

## 4. What to preserve now (cheap insurance)

Already satisfied by the specs, but stated here so it is not lost in refactoring:

- **`place_id` is canonical.** Entity resolution across grid, listings, deltas, and client history
  keys on Google's ID, never a provider-assigned identifier. Any provider that cannot return it
  is disqualified regardless of price.
- **Raw payloads are retained** (storage spec §6). Re-parsing historical responses under new
  assumptions is possible; re-fetching them is not.
- **Grid geometry is ours, not the provider's.** Centroids, radius, and spacing live in
  `scan_snapshot` and are generated by our own pinned function. A provider switch must not change
  where we scan.
- **Provider calls SHOULD be isolated behind a thin internal module** even though the system is
  deliberately not abstracted behind a provider interface. Thin isolation costs nothing; a full
  abstraction built against one implementation is speculative work.

## 5. Triggers to watch

| Trigger | Response |
|---|---|
| Pricing increase >2× on Maps SERP | Evaluate alternatives; economics assume ~$0.0006/point |
| Billing-model change (e.g. the Sept 2025 depth-based shift) | Re-model cost before next cycle |
| Maps endpoint deprecation or coordinate-targeting removal | Immediate parallel-run evaluation |
| Acquisition or service-terms change | Assess, do not panic-migrate |
| Sustained completeness degradation | See below |

**Completeness monitoring doubles as provider health.** PRD §9a.3 marks snapshots below 98% of
expected points as incomplete. A rising incomplete rate that is not explained by our own quota or
geometry problems is the earliest available signal of provider degradation — before pricing
notices, before support tickets. Track incomplete rate as a provider-health metric, not only as a
data-quality gate.

## 6. Component migration effort

| Component | Effort | Notes |
|---|---|---|
| LLM citation checks | Low | Direct provider APIs are a viable fallback; web search must be enabled |
| Organic SERP + paid parse | Low | Commodity; several providers, days of work |
| AI Overview | Moderate | Fewer providers carry it; verify before assuming |
| AI Mode | Moderate | Newest surface, thinnest provider coverage |
| **Maps geogrid** | **High** | Capability requirement in §2 plus the parallel-run in §3 |

A partial migration is legitimate. Nothing requires one provider for everything — the reason for
consolidating today is `place_id` consistency and operational simplicity, not a technical
coupling. Moving the LLM layer to direct provider APIs while keeping Maps on DataForSEO is a
reasonable intermediate state if pricing shifts unevenly.

## 7. What this note is not

Not a plan to migrate. DataForSEO is the correct choice for the reasons recorded in PRD §15a, and
nothing here should be read as hedging. This exists because the cost of writing it now is one
page, and the cost of reconstructing it during an outage or a pricing shock is considerably more.

Review annually, or on any §5 trigger.
