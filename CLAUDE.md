# Claude Code Context

This document gives you (Claude Code) the context to keep building **AR Tools**, an internal agency suite. **Read this first before any other action.**

> **Suite context (read alongside this file).** AR Tools is a **multi-module suite** — Blog Writer, Local SEO content, Keyword research, Organic + Maps rank trackers, an AI-visibility tracker, a Ranking-drop agent, and a VA content scheduler — sharing one dashboard, one Supabase database, and one scheduler. For suite-level scope, the locked architectural decisions, and the phased roadmap, see **`docs/suite-architecture-and-roadmap-v1_0.md`** (this is the product/architecture authority for "how many tools is this"). The Blog Writer's engineering spec and module PRDs remain authoritative for that module's *internals*.

## What this project is

An internal agency suite for SEO/content work across multiple SMB clients. The team picks a client, then works across SEO modules from one dashboard. The first and most-built module is the **Blog Writer**, which generates SEO + AEO-optimized content through a five-module pipeline: enter a keyword for a configured client and the platform produces a publication-ready Markdown article (and can publish it as a Google Doc in the client's Drive folder).

This is **not** a customer-facing SaaS. There's no billing, no customer signup, no marketing site. Internal team use only.

**Brand voice & ICP enforcement — built 2026-07-31 (the client's guide, made enforceable).** Every generator already *received* a client's brand voice + ICP as prose in the prompt, but nothing distilled them into rules, nothing outranked the generator's own defaults, and nothing checked the output — so pages scored "good" on the 8-engine SEO/AEO rubric while failing a human brand-voice audit (found on First Class Roofing: pages scoring 81–85 with the guide loaded). Three root causes, all fixed: (1) **the instructions carried a fake ICP** — `_build_seo_checklist` stated `_detect_icp_from_keyword(keyword)`, a canned label/tone/CTA from keyword modifiers, and the gen system prompt's rule 14 told the writer to match *that* ICP's tone exactly, so a three-word guess outranked the client's real ICP document; (2) **the system prompt contradicted the guide on expression** — it preferred third person over "we/our" (rule 1), mandated a `[Power Word]! …` title formula, and hard-coded CTA examples, all from the cached system slot; (3) **nothing measured it** — `ScorePageRequest` didn't even accept `brand_voice`/`detected_icp`, and `/reoptimize-page` didn't either, so every reoptimize pass rewrote the page with the guide absent. **The core** is `writer/nlp-api/voice_card.py` (pure, unit-tested `tests/test_voice_card.py`): a **Voice & Audience Card** distilled once per guide revision (tone, **grammatical person**, must-use / never-use / discouraged terms, CTA language, the real audience's pains/triggers/motivations/objections; banned-term bar deliberately as high as the blog writer's, plus a stoplist so a distillation artifact like "never use 'we'" can't hard-block every page), a **late high-priority prompt block** (`render_voice_card_block` — explicitly wins on person, word choice, tone and CTA wording; layout requirements still win, or AEO collapses), `resolve_icp_directives` (replaces the keyword heuristic, which is now a fallback for clients with no ICP), and **deterministic checks** (`check_voice_compliance` — forbidden terms by word-boundary regex = `critical`, missing required phrasing / wrong person by density / no CTA resembling the guide = `warning`). An LLM judge can be talked out of a verdict; a regex cannot. **Enforcement:** a `critical` finding triggers targeted corrective rewrite passes (`MAX_VOICE_CORRECTION_PASSES`=2, fed `violations_to_corrections` — named words to remove, far better rewrite input than a score); persisting violations are surfaced, not silently shipped. **Scoring — a SEPARATE scorecard, not another SEO engine (owner ruling 2026-07-31):** brand voice gets its **own 0–100 headline score** beside the SEO composite, never folded into it (a 10% engine can't move a composite enough to matter — a page at 40 on voice would still read "good" — and burying voice inside an SEO number is what let it be ignored). Eight weighted dimensions, each 0–100 with a **verbatim evidence quote from the page**: tone (does it hold across EVERY section, not just the intro), writing_style (rhythm/formality/jargon vs the guide), person, vocabulary, audience_fit (the ICP's actual customer vs a generic buyer), pain_points (their stated worries + objections), cta_fit, and **distinctiveness** ("could this be dropped on a competitor's site by swapping the name?" — the single most useful signal). A dimension the guide is silent on returns `applicable:false` and the remaining weights **renormalize**, so a guide that never mentions sentence rhythm isn't penalised for it. The deterministic checks **cap** the dimensions they've already disproved (`_DETERMINISTIC_CAPS`: a forbidden word caps `vocabulary` at 40, a person mismatch caps `person` at 40) so a generous judge can't hand-wave past a regex match. Assembled by `voice_scorecard` (score/band/dimensions/violations/deficiencies/**`needs_rewrite`**) via `_voice_scorecard_from`, which **pops `brand_voice` out of the scorer response before the composite is computed** — so voice can never leak into the SEO score or the SEO deficiency list (`brand_voice_fit` is deliberately absent from `_ENGINE_LABELS`). The SEO weight maps are therefore **unchanged for every client, forever**. `icp_alignment` stays a 5% SEO engine but is repointed at the real ICP. **Enforcement now triggers on either signal** — a deterministic `critical` OR a scorecard below `VOICE_PASS_THRESHOLD` (80) — and each corrective pass is fed BOTH the named forbidden words AND the failing dimensions with their evidence quotes (`voice_deficiency_text`), then **re-scores** so the stored verdict describes the page that actually ships. Persisted as the full scorecard on `<page>.voice_violations` (jsonb) + the headline number lifted into **`<page>.voice_score`** (migration `20260731130000`, applied live) so it's sortable/filterable and rides the list queries beside `composite_score`. **Coverage (all four generators):** Local SEO (`/generate-page`, `/reoptimize-page` — which now receives the guide at all, `/score-page`), Ecommerce (`/generate-ecommerce-page`, `/reoptimize-ecommerce-page` — the keep-best loop picks on score, so the winner still clears the check via `_ecommerce_fix_voice`, `/score-ecommerce-page`), Service/Location (scored via `/score-page`; its writer already reused the blog distillation), and the Blog + Service writers (`pipeline-api/modules/writer/voice_compliance.py`, unit-tested — adds the person + preferred-phrasing checks alongside the existing banned-term hard-abort; `BrandVoiceCard` gained **`person`**, threaded into the section prompts; findings land on `WriterMetadata.voice_violations` — additive metadata, so **no writer schema bump**). **Caching:** `platform-api/services/voice_card_service.py` distills via `POST /distill-voice-card` and caches on `clients.voice_card` keyed by a SHA-256 fingerprint of the *rendered* guide + ICP text (so a re-scan timestamp doesn't force re-distillation but a real edit always does) — one call per guide revision, not per page, which matters because bulk-create runs one job per keyword. The fingerprint is implemented in both services and **locked by a cross-service unit test**. Every path is best-effort: a distillation failure returns an empty card and everything degrades to prior behaviour — a page must never fail to generate because we couldn't summarise a brand guide. **Also fixed:** a run whose frozen snapshot has neither brand guide nor ICP used to complete silently (the Writer degrades to `1.9-degraded`) — that is how First Class Roofing's one blog post was written with *zero* voice context 11 minutes before their guide was saved; `run_dispatch` now logs it and emits a `content_no_brand_context` warning notification, deduped once per client. ## Railway: read the live config, do not infer it

**Before you change or trigger a Railway deployment, read the live config with `get-service-config` and `list-variables`.** That is the whole rule. What follows explains why it is worth a tool call every time, and is *not* a list to reason from.

This section replaced a growing list of traps, because the list caused the failure it was meant to prevent. A deployment ran the wrong command and spent money; the cause was a dashboard `startCommand` override that silently replaced the image's `CMD` and dropped every flag. But a plausible explanation was already written down — "redeploy replays the old config snapshot" — and it was believed instead of measured. It was even true in general, and false here. **One `get-service-config` call would have shown the real start command immediately; three PRs of reasoning from documentation did not.** A file of remembered traps invites exactly that substitution, so treat the notes below as evidence that this environment's config diverges from what any artifact in the repo implies — never as a substitute for looking.

**What the live config has actually contradicted here** (each cost real time or money):

- A dashboard `startCommand` override that had drifted from the Dockerfile `CMD` for weeks — the repo file was honest and irrelevant.
- `builder` reported as `RAILPACK` by the config API while `railway.toml`'s `DOCKERFILE` is what actually builds. Same endpoint, one stale field and one live one.
- `source.branch` still pointing at a long-merged branch, so a Deploy click faithfully built months-old code.
- Auto-deploy off, which does not merely stop deploys on push — Railway stops *tracking new commits at all*, pinning the service to its last-built commit. A source repoint is then real in config and inert in practice.
- `redeploy` replaying the previous deployment's config snapshot rather than applying a changed start command. Only a fresh deployment picks config up, and no MCP tool creates one for an existing service (`create-deployment` makes a *new service*; `update-service` applies on the next deployment). That means the dashboard, or a push with auto-deploy on.

**Do not trust the run's own status either.** A crashed job reports deployment status SUCCESS under `restartPolicy: NEVER` and posts a green commit status; grep the job's own marker instead (`OUTREACH_RESULT` for outreach). The log stream lags the container, and the Railway agent reads that same lagging stream, so it is not corroboration — check what the job wrote to the database. The deployment's branch label is stale; the SHA is the signal.

**The durable version of all of this is a startup banner**, because a banner reports the config that actually loaded rather than the config someone believed. `outreach` prints commit SHA, branch, resolved command and confirm token as line one, and that is what finally proved which explanation was right.

**For anything that spends money, a safe default is not sufficient on its own** — a *leftover* paid value is the common case, not an absent one. `spend_denial` (`outreach/api/scripts/run_market.py`) is the pattern: the safe command is what you get by omission, and a paid command additionally requires `OUTREACH_CONFIRM_SPEND` to equal that command's own name, so a stale or half-updated config carries a confirmation naming the wrong command and refuses.

### Naming

- Modules and files: `snake_case.py`
- Classes: `PascalCase`
- Functions and variables: `snake_case`
- Constants: `UPPER_SNAKE_CASE`
- Pydantic models: `PascalCase` ending in purpose (e.g., `ClientCreateRequest`, `RunDetailResponse`)

### Error handling

- Always raise `HTTPException` with a string error code in the detail (matches the standardized error envelope from Engineering Spec §5.0)
- Never expose stack traces to the frontend — log them server-side, return `internal_error` code
- Use `try/except` around external API calls; map provider errors to platform errors

### Logging

- Use `structlog` (or stdlib `logging` with JSON formatter) for structured JSON logs to stdout
- Always include `run_id` and `request_id` in log lines via context vars (Engineering Spec §13)
- Never log: JWTs, full brand guide text, API keys, user passwords

### Database access

- All Supabase calls from the backend use the **service role key** (not anon key) — RLS would block service operations
- Always wrap Supabase calls in try/except; map errors to user-friendly responses
- Schema changes go through migrations in `writer/supabase/migrations/` (apply to the live project via the Supabase MCP when working web-only)

### Testing

- Existing tests are pure service-logic units mocked with `unittest.mock` (see `writer/platform-api/tests/`); there is no FastAPI `TestClient` harness yet

## Things to ask before doing

These decisions are not in the docs — ask the user:

1. Specific Anthropic model selection per module (Sonnet vs Opus per task), where not already chosen in code
2. Specific prompt copy for distillation, reconciliation, website/GBP extraction (the docs describe behavior, not exact prompts)
3. Observability tooling beyond stdlib logging (Sentry, Better Stack, etc.) — planned for v2
4. Whether to add automated tests in CI on push, or rely on manual testing
5. Branch protection rules and PR requirements
6. Alerting/notifications delivery channels (in-app feed vs email/Slack + the provider/webhook details) before building the notifications service / rank-tracker alerting

> **Resolved:** the **shared scheduler** mechanism is decided — an in-process asyncio loop in platform-api (`services/gsc_scheduler.py`) that enqueues jobs into `async_jobs`; reuse it for future scheduled trackers rather than adding new infra.

## Things NOT to do without asking

- Don't change the service topology (e.g., split modules into separate Railway services)
- Don't add a queueing system beyond the `async_jobs` table
- Don't introduce new external dependencies (Redis, Celery, RabbitMQ, etc.)
- Don't add a caching layer in front of Supabase
- Don't change the brand-vs-SIE precedence rules
- Don't reverse a locked decision in the suite roadmap's decision log
- Don't expose the pipeline-api or nlp-api publicly — they must remain on Railway's private network (the `nlp` service is intentionally private + auth-less)
- Don't implement features marked "out of scope for v1" in the PRDs (e.g., live-to-CMS publishing)
- Don't re-add the Local SEO features cut from v1 (client-site brand-voice/ICP scraping, the keyword-worthiness "rankability" check, billing/credits) without agreement — see the integration plan
- Don't edit `/local-seo-writer` expecting it to ship — it's the raw reference copy; active Local SEO work goes in `writer/nlp-api/` plus the suite frontend/backend

## When you're stuck

If something seems underspecified or contradictory, stop and ask. The user has been deeply involved in spec design and prefers a quick clarifying question over a wrong assumption that's expensive to undo.

## How to communicate progress

After completing a meaningful chunk of work, summarize what you did, what you tested, and any open questions. Don't wait until everything is built to report status.
