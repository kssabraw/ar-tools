# Location-page quality — verify-and-tune (2026-08-27)

**Task:** confirm the 2026-08-27 Local SEO tuning (length_fit #781, Lever 2
mid-page voice-drift localizer #792, two-axis keep-best corrective pass) fires
correctly for **location** pages (`<service> <suburb>`, page_type
`location`/`city_service`), and tune anything location-specific.

**Verdict: no code gap.** Location pages inherit all three improvements
identically because they are generated by the *same* one code path as flagship
local landing pages. This is a verification, not a port. Deliverable = this
confirmation + a live A/B on a real location page.

---

## Task 1 — do the improvements fire for `location` / `city_service`?

**Yes, identically.** There is exactly **one** local-page generator. A flagship
"`<service> <city>`" landing page and a "`<service> <suburb>`" location page go
through the same `local_seo_service.generate_page` → nlp-api `POST /generate-page`
path, byte for byte. Evidence:

- `nlp-api/main.py::GeneratePageRequest` has **no `page_type` field** — the
  generate endpoint never branches on page kind.
- The `page_type` values `location` / `city_service` exist only in
  `classify_page_type` (main.py:2462+), a **URL classifier** for discovering /
  classifying *existing* pages on a client's site (reoptimizer + silo
  existing-page check). They never touch generation.
- `local_seo_service.generate_page` (local_seo_service.py:475) and its payload
  builder `_gbp_to_generate_payload` carry no page-type discriminator.

Every improvement is therefore inherited unconditionally:

| Improvement | Fires in | Gate (none location-specific) |
|---|---|---|
| **length_fit** (0.10 engine) | `_score_html_inline` (main.py:4284) + `_score_page` (6023) — the exact scorers generation uses; folded into the composite via `_ENGINE_WEIGHTS` | only that a `serp_word_target` exists |
| **Lever 2 voice-drift localizer** | `_localize_voice_drift` inside `_seo_voice_correct_inline` (main.py:4628) | `VOICE_LOCALIZE_ENABLED` + a voice guide + ≥1 `<section>` |
| **Two-axis keep-best corrective pass** | generate loop (main.py:7283–7360) | voice `needs_rewrite` OR SEO composite < threshold w/ a deficient engine |

## Task 2 — is the length target right for the tighter location format?

**SERP is geo-modified for the suburb.** `fetch_serp_urls` (main.py:1186) queries
DataForSEO with `keyword` as the phrase and location/location_code as the geo.
Location targets carry the suburb *in the keyword*
(`local_seo_silo._neighborhoods_for_city`: `page_kw = f"{keyword} {name}"`, e.g.
"IT Support Company Winter Park"), queried at the metro. So the measured
competitor SERP is the suburb's SERP. ✔

**The reference mirror is scaled to the SERP target, never copied from a bigger
page.** `generate_page` sets `serp_target = serp.serp_word_target`
(`= max(SERP_avg×1.20, 900)`), then renders the client reference (local_landing
preferred, else location) via `render_reference_structure(..., target_words=serp_target)`
— always `mode="full"`. `scale_analysis_words` rescales the reference's
per-section words so the **outline sums to `serp_target`**, preserving layout
while retargeting size. A 3,177-word flagship reference is scaled *down* to the
suburb SERP budget. The target is never an inflated copy of a bigger reference. ✔

**Observation (owner product question, not a bug).** For a thin suburb term the
pages that actually rank are often competitors' big *metro* flagship pages
(nobody has a suburb page), so the measured `serp_avg` — and the length target —
can be genuinely large. This is inherent to the SERP-driven design and is
*identical* to flagship behavior. Whether a location page should be deliberately
shorter than its flagship is a **product decision**, and the plumbing to
differentiate the two at generation time does not exist today (by design — one
generator). Flagged for the owner; not built.

## Task 3 — does the localizer behave on a location page's shorter section set?

**Yes.** `section_edit.split_sections` returns however many top-level `<section>`s
the page has; `section_digest` lists each; the Haiku audit reports ≤6
worst-drifting; `_build_drift_block` (unit-tested, `test_voice_localize.py`) drops
unknown keys, dedupes, caps at 6, and returns `""` → the page-wide sweep fallback
when empty. On a short location page the corrective pass can sweep every section
anyway, so the localizer is at worst a no-op benefit, never harmful. ✔

## Empirical evidence (production data)

Only two clients have Local SEO pages. **Wheelhouse IT Orlando** has ~40 genuine
`<service> <suburb>` location pages — the exact format ("IT Support Company Winter
Park / Windermere / Conway / Belle Isle / Azalea Park / …", location = Orlando
metro):

- Pre-tuning (2026-07-22/23, before length_fit + the voice system): composite
  **75–88** (mostly low-80s), body ~**17–22k html-text chars** (~2,700–3,400
  words), **no voice_score** (the voice system shipped 2026-07-31).

**First Class Roofing** flagship service pages, *post*-tuning (2026-08-27):
composite **75.5–87.3**, voice **77.8–87.0**, body **~12–18k chars** (length_fit
effect vs the ~21–25k pre-tuning pages); latest #792 baseline voice **83.5** /
composite **84.4**.

## Live A/B — matched location keyword (Wheelhouse "IT Support Company Winter Park")

Re-generated the identical location keyword on the current pipeline for a matched
before/after (new page `290ecbb5`). (The first attempts were killed mid-run by an
unrelated PLATFORM deploy storm — four deploys 18:22–18:53 UTC for PRs
#740/#794/#796; the clean run below is on the stable #796 deployment. It ran 27 min,
slowed by Anthropic 429 backoff on the shared account — see the caveat.)

| | Composite | Voice (band) | Body words | length_fit |
|---|---|---|---|---|
| Before (2026-07-22, pre-tuning) | 85.0 | — (no voice system) | ~3,200 | — (engine didn't exist) |
| After (2026-08-27, current) | **82.1** (good) | **80.9** (drifting, full analysis) | **1,463** | score 57.6 · target **1,058** · SERP avg **882** |

**What the live A/B proves:**

1. **length_fit fires for the location format, on the suburb SERP.** It measured
   the "IT Support Company Winter Park" SERP (avg **882 words**), set target
   **1,058** (882 × 1.20), and scored the page — the definitive confirmation the
   length engine is active for a `<service> <suburb>` page and reads the
   geo-modified SERP, not a metro one.
2. **The voice scorecard + localizer path ran** (`analysis: "full"`, 8 dimensions,
   **80.9** — passes the 80 threshold, band "drifting"), in the FCR-comparable
   post-tuning band (FCR flagship voice 77.8–87.0).
3. **Length collapsed ~54%** — from ~3,200 words (pre-tuning) to **1,463**. The
   2–3× bloat length_fit was built to kill is gone on the location format too.
4. Composite 82.1 < pre-tuning 85.0 **because** length_fit (a new 0.10 engine that
   didn't exist pre-tuning) honestly penalizes the residual overage; the old 85.0
   never accounted for the page being 3× over target.

**Finding (Task 2, data-backed — owner decision, not built):** even after the
~54% cut, the page lands **38% over its 1,058-word target** (1,463 vs 1,058), which
is **just under** the generation-time length-trim threshold (`LENGTH_TRIM_MIN_RATIO`
= **40%**), so no trim pass fired and `length_fit` scored **57.6**, dragging the
composite by ~4 pts. On the *smaller* location-page target this 38% is only ~400
words; the identical 400-word overage on a ~2,000-word flagship target is ~20% and
wouldn't come near the trigger — so the trim threshold bites *less* on exactly the
narrower format that most needs it. Two levers, both owner calls (and both wanting
several runs, not this one 429-degraded sample, before a change):
(a) lower `LENGTH_TRIM_MIN_RATIO` (adds a ~90s trim+rescore to more pages — the
comment deliberately set 40% to keep the trim "a rare safety net"); and/or
(b) tighten the writer's in-prompt word-budget adherence so it doesn't overshoot
by 38% in the first place.

**Caveat on the numbers:** this run was rate-limited (27 min vs the usual ~11), and
the two-axis corrective loop is gated by `GENERATION_TIME_BUDGET_SECONDS`, which
counts wall-clock — so the 429 backoff likely starved some corrective/trim passes.
Voice 80.9 and length_fit 57.6 are therefore a **floor**; a clean run would plausibly
score higher and might have trimmed closer to target. This is why the length finding
is flagged for measurement across several clean runs, not acted on from n=1.
